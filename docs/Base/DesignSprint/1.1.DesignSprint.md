
# 1.1. Design Sprint  

**Design Sprint** é um processo estruturado de cinco dias criado pela [GV (Google Ventures)](https://www.gv.com/sprint/), que tem como objetivo responder perguntas críticas de negócios por meio de design, prototipagem e verificação/validação.

A proposta do Sprint é acelerar o aprendizado: em vez de passar meses discutindo ideias ou aguardando o lançamento de um produto mínimo para avaliar sua aceitação, a equipe constrói em poucos dias um protótipo realista e coleta dados claros a partir do feedback dos usuários.

# Aplicação no Projeto
Durante o desenvolvimento da nossa solução dentro do Design Sprint utilizamos os seguintes processos criativos e ferramentas dentro das fases do **Design Sprint**:

## [Unpack](Base/DesignSprint/1.1.1.Unpack.md)

Nessa fase inicial, a equipe mergulha no problema. É o momento de compartilhar informações, levantar hipóteses, analisar o contexto, entender os usuários e mapear os principais desafios. Entrevistas, discussões abertas e análises ajudam a alinhar o conhecimento de todos os envolvidos.  

- **Brainstorm inicial**: Coletamos ideias de projetos sem filtros para explorar diferentes possibilidades. Após votação, uma ideia foi escolhida como foco principal, e cada membro sugeriu funcionalidades adicionais.
- **Lean Inception**: Utilizamos da metodologia de forma adaptada para o nosso contexto com o objetivo de pegar o que fizemos no Brainstorming inicial para gerar ideias mais claras e concretas sobre a visão do produto, personas que iriamos abrangir e features inicias do projeto. 

## [Sketch](Base/DesignSprint/1.1.2.Sketch.md)

Com o entendimento consolidado, cada participante gera propostas de solução de forma visual, geralmente de maneira individual. O objetivo é explorar diferentes ideias criativas e traduzir conceitos em esboços que possam servir de base para a decisão.  

- **Rich Picture inicial**: Todos os integrantes desenharam representações visuais do sistema, permitindo diferentes perspectivas do projeto.

## [Decision](Base/DesignSprint/1.1.3.decision.md) 

As ideias apresentadas são discutidas em grupo. A equipe analisa os pontos fortes e fracos de cada proposta, identifica padrões e escolhe as soluções mais promissoras para seguir adiante.  

- **5W2H**: Estruturamos ações e responsabilidades, detalhando o quê, quem, quando, onde, por que e como as funcionalidades seriam implementadas.
- **Diagrama de Causa-Efeito**: Identificamos causas possíveis para problemas e desenhamos relações entre elementos críticos do sistema.
- **Brainstorm final**: Discutimos e refinamos ideias com base nas análises anteriores.
- **Rich Picture (Final)**: A partir dos rich pictures iniciais, escolhemos uma versão que melhor representava a solução final acordada pelo grupo.

## [Prototype](Base/DesignSprint/1.1.4.Prototype.md)

Aqui, a equipe criou um protótipo funcional e interativo, que simula a experiência final do usuário. A prioridade é a velocidade: o protótipo não precisa ser perfeito, mas deve ser convincente o suficiente para que possa ser avaliado de forma realista.  

- **Protótipo baixa fidelidade**: Desenvolvemos a primeira versão simplificada do aplicativo para testar conceitos básicos.
- **Protótipo de média fidelidade**: Foram feitas telas alinhadas com as features inicias que foram decididas para o projeto no Figma, mas ainda sem com forma de navegação.
- **Protótipo alta fidelidade**: Construímos a versão final no Figma, pegando como base as telas do de média fidelidade, com os elementos visuais principais interativos prontos para validação.

## [Validate](Base/DesignSprint/1.1.5.Validate.md)

O protótipo foi colocado à prova diante de usuários reais para observar reações, colher feedback e identificar se a solução realmente resolve o problema proposto. Além dos testes diretos, essa fase também pode envolver benchmarking, ou seja, a comparação da proposta com soluções já existentes no mercado.

- **Validação com possíveis usuários**: Testamos o protótipo com pessoas que se encaixam no perfil do usuário turista que é o usuário principal da aplicação pelo formato de um checklist no forms. O intuito era validar nosso protótipo em relação a perspectiva do turista dentro da plataforma, e se as necessidades de acordo com o intuito do projeto foram comtempladas com o que foi trazido no protótipo. Além de validar se o fluxo de interação também estava fazendo sentido.
